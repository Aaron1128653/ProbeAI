# Demo runbook (D17, D18)

One live run, in record mode, on the seeded TaskBoard app; a labelled REPLAY of a real earlier run as the fallback. The code is frozen (D17); this page is what changes if anything does.

## Start (three terminals, from the repo root, PowerShell)
| What | Command | URL |
|---|---|---|
| Demo app (the thing being tested) | `.venv\Scripts\python.exe -m uvicorn demo_app.server:app --port 8765` | http://127.0.0.1:8765/ |
| Live tester (real API, records the run) | `$env:PROBE_LLM_MODE="record"; $env:PROBE_WEB_YES_SPEND="1"; .venv\Scripts\python.exe -m uvicorn web.server:app --port 8000` | http://127.0.0.1:8000/ |
| Fallback tester (REPLAY, costs nothing) | `.venv\Scripts\python.exe demo_fallback\start_replay.py` | http://127.0.0.1:8001/ |

Stop any of them by the PID that owns its port, never by image name (other work runs on this machine):
`Get-NetTCPConnection -LocalPort 8000 -State Listen | Select-Object OwningProcess` then `Stop-Process -Id <that pid>`. **Never `taskkill /IM python.exe`.**

**The fallback** replays the committed fixture `demo_fallback/fixture/rehearsal5_llm_record.jsonl` (D18): a byte-for-byte copy of the model-call record of rehearsal 5 (a real run on 2026-09-24: completed, delete bug Confirmed, the repeat-guard line; provenance `runs/web_c5333263`). sha256 `bda600a35bdf1c475eebf2ae41a92db9e20e187dc037b7f0e047695bfbcd3067`; the launcher prints `pinned fallback OK` and **refuses to start on a mismatched fixture**; `Get-FileHash` should agree. It survives a clone, a moved folder and a cleaned `runs/`. `start_replay.py` sets `PROBE_REPLAY_MAX_MISSIONS=3` - the server default is one mission and one mission of this recording finds nothing (pinned by `tests/test_d17_fallback.py`). Dress-rehearsal and stage recordings stay in `runs/`; they are never promoted to the fallback (replacing the fixture needs a `/decide`).

## During the demo
1. Click **Run test** once. The plan appears at about 7 s: **read the three missions aloud** ("it chose these itself") before results arrive. A run takes about 55 s (range so far 52-67 s).
2. Present **whatever the run shows, as it is.** Branches:
   - **A. Completed, Confirmed card** -> narrate the Confirmed card, then the Likely items, then the guard log line if present.
   - **B. Amber banner, Confirmed card present** -> read the banner aloud, then say exactly: *"This run did not finish every check, and the page says so rather than hiding it. The Confirmed card is a separate question: that bug was reproduced in a clean replay before the run ended, so it stands. But the sweep did not finish. So if nothing else is Confirmed, that does not mean the app passed."* (D19) If asked why the check did not finish, read that mission's log line and say only what it shows; for the shape where the AI said `stuck` after one failure: *"In that check the AI stopped after one failure. My stop rule needs the same failure twice, so it did not apply, and I don't let the AI's own 'stop' count as finished."* Never "conservatively", "safely", "correctly" or "as designed" about a `stuck`.
   - **C. No Confirmed card (completed or amber)** -> look at the three missions you read out. If none was a delete check: *"This run didn't test delete. The AI did propose it - fourth of five - and the live mode runs its top three to stay near a minute; that's my speed-versus-coverage choice."* Show what it did find. If a delete check ran but nothing was Confirmed: *"It tested delete and did not confirm it this run; I'll look at that recording afterwards."* (After the talk: zero-cost inspection of the recording via `/decide`.) Then open REPLAY with the introduction below.
   - **D. Red failed status, API or network error** -> say *"The live call failed - that is the network or the API, not a result,"* and open REPLAY with the introduction below. Do not say the live requirement was met by this run.
3. **No silent re-run. Ever.** A second live run is allowed only after a red failure, or if the panel asks, and it is announced as "a second sample" and never replaces the first.
4. **Never say "it always finds the delete bug", and never give a percentage.** Say counts you can show: "After the last fix I ran it three times through this page. All three found real planted bugs and none reported a false one. Two of the three finished every check, and one of the three met my full demo bar - finished, delete bug confirmed and shown first." If asked how often it looks like that: "Three runs is too few for a percentage. What I can show you is in the recordings: the AI proposed a delete check in all 26 plans, ranked it fourth in 6 of them, and when a delete failed it tried again in 14 of 15." The 7-in-10 figure in D17 is an internal planning estimate, not a result; it is not said and not on a slide.
5. **REPLAY introduction - say it every time, before anything on that tab** (the banner has no date, so you must): *"What I'm switching to now is not live. It is a recording of a real run from the 24th of September - the orange REPLAY banner says so - played back through the same page without calling the AI, which is why it takes about 11 seconds instead of 55. I'm using it to show what a confirmed finding looks like, not as a second result."*

## What to say about the six real runs
"I ran the finished tool through the real web page six times against my test app. The first three took 58 to 67 seconds; each found the planted delete bug and proved it by repeating it, but each ended with an amber 'did not finish' warning, because the AI kept pressing the same broken Delete button. I added a plain rule - if the same button fails with the same server error twice, stop that check - and ran three more, unchanged in between. Those took 53 to 55 seconds and 12 or 13 AI calls, about five cents each. One was clean: delete bug confirmed, rule fired, no warning. In one the AI gave up after the first failure, so the rule never came into play and the warning showed, correctly. In one the AI ranked the delete check fourth, the live mode runs three, so the delete bug was never tested; it still found two other planted bugs. Across the three post-fix runs, every item it reported was a real planted bug. So of the three runs after the fix, two finished every check and one met my full bar - three runs is too few to turn into a percentage, so I won't."
