# Audit guide (for an independent reviewer)

Project: ProbeAI, an AI web-app tester built as a take-home engineering exercise. Written 2026-09-21 (end of day 1), updated 2026-09-22 (day 2: T5, an independent review of it, three fixes, and the first real API call), updated again same day (T6 live UI, D11's pre-evaluation hardening and its own independent review, and the first real N=5 buggy + N=5 clean evaluation batch), updated 2026-09-23 (D12's evidence-based failure attribution and the single-variable judge-evidence change it justified, the N=3 verification, D13's one-call disprove contract check, and D14's judge-verdict scoping), and updated 2026-09-24 (T12's presentation hardening, the first real run through the web UI, D15's audit of the amber banner, and T13's precise-wording change). Nothing here asks you to trust the author: every claim has a command or a file you can check.

## 1. How the work was produced
- The owner (Yuanhang Wang) sets goals and approves direction; they are a mechanical-engineering PhD student, not a professional software engineer.
- **Claude Opus** made design decisions and wrote them into `docs/DECISIONS.md` (D1-D9), `docs/PROMPTS.md`, `docs/RESEARCH.md`.
- **Claude Sonnet** wrote the code from those specs. Through T4 (commits up to `56df798`) this ran as a separate `builder` subagent (`.claude/agents/builder.md`), reporting back self-reported results that Opus then independently re-ran (see section 4). **T5-0 and T5 (`bd860d9`, `613ac45`) were different**: the `/build` command routed the same conversation to run as Sonnet directly, with no separate Opus pass at the time - the review below is exactly that missing pass, done afterward at the owner's explicit request.
- **The owner then asked for an independent `/review` before any real API money was spent.** Opus read `probe/agent.py` and `probe/llm.py` fresh (not the WORKLOG self-report), reproduced three real bugs directly (not just by inspection), and gave a prioritized fix list; the owner approved the top three, and Sonnet fixed them with regression tests, each mutation-confirmed against the pre-fix code (commit `0b4662c`). This is the pattern the project is meant to follow, and it worked as intended: a same-turn self-check had already produced 213 passing tests without ever exercising the actual `.env`-loading order, the out-of-range step path, or the missing deadline check - a second, independent, adversarial read caught all three before they could cost money or crash a live demo.
- Important limit: the same model family wrote and reviewed the work throughout. An outside reader should re-run things and read the code, not just this file.
- The git history is the trace: one commit per task, decisions committed before the code that implements them.

18. **The judge's step verdict contradicts its own finding in 4 of 95 recorded judge calls, and all four are the same bug** (D13 Part 1). Not scattered noise: the counter defect every time. Checked by mutation (threshold, `stuck_reason` check, `timed_out` check, both page branches, and the per-mission count - the last one **survived the first version of its own test** and was strengthened). The real recorded run was also replayed at zero cost through the new code (`runs/web_e9ab64af/llm_record.jsonl`, replay mode): `m3` -> `stuck` / `model_declared` / 3 server failures, counts identical to the real run (1/1/0/1), `run_status` `partial`, reason set. Deliberately left as an open V2 question with n=1: whether the model should have a third terminal action for a deliberate, conclusive stop.

## 6. What is verified, and what is not (as of the disprove contract check, 2026-09-23)
**Verified by real, deliberate, user-approved calls:**
- The first real call (single mission, mode `record`, $0.10 cap, cost $0.020443, 6 calls): `claude-haiku-4-5` does support `output_format=StepDecision` with `thinking: disabled` - D7 point 5's open question is resolved. The `--yes-spend` gate and the cross-run ledger were both exercised for real and behaved as designed.
- **The real T7 evaluation batch** (11 runs, mode `record`, `--n 5`, cost $0.845632, 15.7 min total): the end-to-end pipeline now has produced real, bug-finding reports, not just a quiet non-finding - S1 (delete fails) and S3 (whitespace title accepted) were found with genuine 100% consistency and zero false negatives across 5 independent buggy-build runs. **The prompt-injection canary (D7 point 4) is now tested and passed**, independently verified (not just the printed line) by confirming the adversarial task text was actually present in the page state the model saw. **One genuine false positive occurred on the clean build** (1/5 runs - a judge reasoning error about its own mission's assumptions, not a keyword-matching artifact), giving a real, non-zero "how often does it cry wolf" number rather than a suspiciously perfect zero.
- T6's live UI and T7-0's hardening were each independently `/review`ed fresh (not just self-reported) before being trusted - see items 12-15 above and section 1.
- **S6 (the counter defect) took two distinct fixes, and it is worth keeping them apart** - the baseline number was 0/5 recognised despite the bug happening in 5/5 runs. (i) **The evidence reaches the judge** (T8-b, D12): it was only ever shown a diff of what *changed*, and a counter that fails to update changes nothing, so the defect was structurally invisible. Adding a capped post-step page state took S6 from **0/5 to 3/3** on the measured runs. (ii) **The tiering no longer discards it** (T11-a, D14): even once seen, a judge-only finding was dropped whenever the judge said the step's own expectation was met - which for S6 it correctly was, since the expectation was about the checkbox, not the counter. Scoping that rule to signal-based candidates moves exactly 3 recorded findings from Dropped to Likely and nothing else. Both are needed: (i) without (ii) leaves S6 at the mercy of whether the step agent happened to mention the counter in its expectation; (ii) without (i) has nothing to tier. Locked in by `tests/test_d14_replay_audit.py`, which re-derives the blast radius from the recorded corpus.
- **The disprove pass (D3 step 3) has now executed successfully against the real API - once, on 2026-09-23, and not before that** (D13/T10-b): 675 in / 236 out, 4859 ms, $0.003710, recorded in `runs/disprove_check_2026-09-23/`. Until that day it had never run at all - 0 calls across the N=5 batch, the N=3 batch and the canary - and its `max_tokens` was set to a value it could not have worked at (see item 17). What this verifies is the **contract**: a real call is made, a valid `Disproof` comes back, it is not cut off, and usage is recorded. It verifies **nothing about the quality of its judgement** - one call on one candidate is not a measurement, and it must not be quoted next to the N=3/N=5 numbers.

- **The primary live demo path has made exactly ONE real run so far (rehearsal 1, 2026-09-23, 14 API calls), and that is the whole evidence for it.** Everything before it - 472 real calls - came from CLI entry points (`probe/agent.py`, `probe/evaluate.py`, `probe/check_disprove.py`); the web UI's own recorded runs were `fake` or `replay`. It ended with the amber "did not finish" banner because mission `m3` said `stuck` after three real 500s - audited in D15 (section 5, item 19). - **The prompts have real evidence behind them now, but have not been re-tuned against it.** In the 2026-09-22 baseline, 4 of 6 seeded bugs were never genuinely found across 5 tries. **S6 has since been fixed and is no longer in that list** (see the S6 entry above: 0/5 -> 3/3), and it was fixed by changing evidence and tiering, *not* prompt wording - which is the point. The remaining three (S2, S4, S5) are coverage failures, and D12's attribution points at **mission-planning breadth**, not judge-prompt wording: S2 and S5 were never proposed in any of 25 missions, and S4 was proposed once and starved of step budget before it could act. Needs a `/decide` before any prompt wording changes, per the model split - not touched yet.
- **Step-budget starvation, unfixed and measured**: all 5 baseline runs consumed exactly 15 of 15 run-wide steps and the last mission was starved in 5/5 (`budget_exceeded`). The `eval` profile asks the planner for 5 missions but funds 3-4, so any plan-diversity change would largely reshuffle which missions starve. Recorded in D12, deliberately not bundled with the judge-evidence experiment.
- **Whether the pre-registered expectation itself was valid** is still unmodelled (D14 Part 2, D12's clean-build false positive): one boolean cannot say "the expectation was wrong, not the app". Left open on purpose - the root cause sits upstream in the step agent's state tracking, and the obvious fix would weaken the anti-hindsight device that makes a "Confirmed" defensible.
- 2 of the 6 T5-review findings (item 14) remain open, on purpose, gated on a condition that has not happened: form-action/JS-navigation origin checking and a narrower (not whole-page) fingerprint comparison, both deferred until a third-party site is actually chosen, since TaskBoard has no surface where either could matter.
- Replay assumes the target can be reset (TaskBoard exposes `/__reset`); arbitrary apps with server-side state may not replay cleanly.
- The disprove prompt remains text-only (no screenshot) - an explicit, disclosed D2 boundary ("vision is a later flag"), reconfirmed rather than silently left in D11, formally deferred to V2.
