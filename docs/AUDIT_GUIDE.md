# Audit guide (for an independent reviewer)

Project: ProbeAI, an AI web-app tester built as a take-home engineering exercise. Written 2026-09-21, updated through 2026-10-05. Nothing here asks you to trust the author: every claim has a command or a file you can check.

## 1. How the work was produced
- The owner (Yuanhang Wang) sets goals and approves direction; they are a mechanical-engineering PhD student, not a professional software engineer.
- **Claude Opus** made design decisions and wrote them into `docs/DECISIONS.md` (D1-D9), `docs/PROMPTS.md`, `docs/RESEARCH.md`.
- **Claude Sonnet** wrote the code from those specs. Through T4 (commits up to `56df798`) this ran as a separate `builder` subagent ([`.claude/agents/builder.md`](https://github.com/Aaron1128653/ProbeAI/blob/v0.1.0/.claude/agents/builder.md)), reporting back self-reported results that Opus then independently re-ran (see section 4). **T5-0 and T5 (`bd860d9`, `613ac45`) were different**: the `/build` command routed the same conversation to run as Sonnet directly, with no separate Opus pass at the time - the review below is exactly that missing pass, done afterward at the owner's explicit request.
- **The owner then asked for an independent `/review` before any real API money was spent.** Opus read `probe/agent.py` and `probe/llm.py` fresh (not the WORKLOG self-report), reproduced three real bugs directly (not just by inspection), and gave a prioritized fix list; the owner approved the top three, and Sonnet fixed them with regression tests, each mutation-confirmed against the pre-fix code (commit `0b4662c`). This is the pattern the project is meant to follow, and it worked as intended: a same-turn self-check had already produced 213 passing tests without ever exercising the actual `.env`-loading order, the out-of-range step path, or the missing deadline check - a second, independent, adversarial read caught all three before they could cost money or crash a live demo.
- Important limit: the same model family wrote and reviewed the work throughout. An outside reader should re-run things and read the code, not just this file.
- The git history is the trace: one commit per task, decisions committed before the code that implements them.

> **Note on paths.** The process documents (`WORKLOG.md`, `QA_NOTES.md`) now live in `docs/process/`. After v0.1.0 the talk-planning spec (`DECK_PLAN.md`), the stage runbook (`DEMO_RUNBOOK.md`), the deck build and QA scripts and screenshots, `WRITEUP.docx` and the Windows launchers were removed from the current tree, and `CLAUDE.md` and `.claude/` are kept at tag v0.1.0 only; the slides are now `docs/ProbeAI_deck.pdf`. All of it is in git history. Older entries in `DECISIONS.md` and the work log refer to the old locations on purpose - they are the record as it was.

19. **The first real web-UI run showed an amber "this scan did not finish" banner over a run that had gone fine, and the audit concluded the banner was right** (D15). `m3` chose `action="stuck"` after three real 500s; the prompt defines `stuck` as "cannot proceed" and `done` as "goal tried, outcome observed", and `m3`'s own reasoning matched `done` - a vocabulary miscall by the model, not a system fault. Checked by mutation (threshold, `stuck_reason` check, `timed_out` check, both page branches, and the per-mission count - the last one **survived the first version of its own test** and was strengthened). 21. **D16 / T14: the deterministic repeat guard, and how it was decided** (2026-09-24). The owner pasted an external advisor's (ChatGPT) proposal and asked for an Opus decision, then execution if Opus agreed. An **Opus subagent** evaluated it element by element (agree / adjust / reject), did a zero-cost counterfactual audit before deciding, and wrote D16; Sonnet then implemented T14 exactly to D16's names and thresholds. Same model family throughout, so what is independent here is *reproduction*, not authorship: the Opus audit's numbers (22 runs, 100 missions, guard fires on 13, 0 on the 8 clean runs, 26 cut steps all the identical click) were **re-derived by a separately written test** (`tests/test_d16_repeat_guard_audit.py`), which reproduced them exactly, and the three rehearsal recordings were replayed through the new code at $0.00: all three `completed`, identical tier counts to the real runs, 1-3 fewer model calls. The rule: the same action on the same element hitting the same normalised **hard** signal twice ends the mission as `done` with an audit-visible `terminal_reason`; only browser evidence triggers it, never the model's word, and it cannot create, promote or drop a finding (Confirmed still needs a clean-context replay). Things an auditor should weigh: (i) **it is a behaviour change to what counts as a finished mission**, and it changes `run_status` outcomes (a run that used to read `partial` now reads `completed`) - defensible because the trigger is browser evidence rather than the model's self-report (the distinction D15 drew), but it is the kind of change to scrutinise; (ii) **the counterfactual only measures what the recordings show was cut** - a real re-run diverges after the cut, so the three post-fix real rehearsals were the actual test (their result, and why the bar written for them was itself wrong, is item 22); (iii) **the corpus gate does not defend the 'hard signals only' rule** - including contextual signals changes nothing on the recorded corpus (still 13 / 26), found by mutating it, because no recorded mission repeats an identical contextual failure; that rule is defended by parametrised unit tests instead (also mutation-checked, nine mutations, all caught); (iv) two existing tests were re-shaped from 'same Delete twice' to 'two different Delete buttons' because the guard now correctly ends the same-button shape - visible in the T14-a diff, worth confirming they still test what T13 meant. Prompts, schemas, tier rules, judge, replay, disprove, profiles and the demo app were not touched; `tests/test_prompts.py` passes unmodified.
